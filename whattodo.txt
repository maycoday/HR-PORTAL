# Build a Fast HR Summit HR Registration & Verification Portal

I want you to help me design and build a complete web application for an **HR Summit at MIT India Hackathon**.

## 1. Important Clarification

This is **NOT a participant management portal**.

Do not create concepts such as students, participants, candidates, applicants, or general event participants.

This portal is **ONLY for HR guests/HR professionals attending the HR Summit**.

The purpose of the application is to help the registration desk quickly find, verify, register, and check in HR guests.

---

# 2. The Real-World Problem

We currently have approximately **700 HR professionals** who may attend the HR Summit.

At the physical registration desk, one staff member will operate this portal.

An HR guest will arrive and provide their name or other details.

The desk operator should be able to:

1. Search for the HR.
2. Quickly identify whether the HR exists in our database.
3. See their details.
4. Verify them.
5. Allow entry/check them in.
6. Handle spelling mistakes or incomplete information gracefully.
7. Add a legitimate HR who is missing from the database.

The most important requirement is:

> **Do NOT reject a legitimate HR just because their name is misspelled, incomplete, or slightly different from the database.**

The application should help the registration desk identify the correct person.

---

Our existing Excel data contains approximately 700 HR records.

Current information available includes:

* Full Name

* Company

* Role
* Date of Attendance
* Invited By

There are only two summit dates:

# 4. Core Registration Desk Workflow

The main screen should be extremely simple and fast.

The operator should see a large search box:

"Search HR by name, email, mobile number or company"

When the operator searches:

## Case A — Exact Match

Show a clear green verification card:

VERIFIED

Full Name
Designation
Company
Email
Mobile
Role
Attendance Date
Invited By

Then provide:

**ALLOW ENTRY / CHECK IN**

After clicking it:

**ENTRY RECORDED SUCCESSFULLY**

Store the check-in time.

---

# 5. Case B — Name Not Found

Do NOT immediately show:

"ENTRY DENIED"

Instead show:

**No exact match found**

Then automatically provide possible ways to find the HR:

* Partial name search
* Similar names
* Company-wise search
* Email search
* Mobile search
* Designation search

For example, if the operator searches:

"Rahul Sharma"

the system might show:

Rahul Sharma — ABC Technologies
Rahul S Sharma — ABC Technologies
Rahul Sharma — TCS
Rahul Kumar — ABC Technologies

The operator can identify the correct HR.

---

# 6. Fuzzy / Flexible Search

Search should not depend only on exact spelling.

It should handle cases such as:

"Rahul Sharma"

"Rahul Sharm"

"Rahul S Sharma"

"rahul"

"RAHUL SHARMA"

The search should be case-insensitive and support partial matching.

If practical with the selected database, implement fuzzy/similarity search as well.

Search should work across:

* Name
* Company
* Email
* Mobile
* Designation

---

# 7. Company-Wise Search

This is very important.

If an HR says:

"I'm from Deloitte"

the operator should be able to search/select:

Deloitte

and see all matching HRs from that company.

Example:

| Name        | Designation | Date   | Role     | Status     |
| ----------- | ----------- | ------ | -------- | ---------- |
| Rahul Mehta | HRBP        | 22 Aug | Delegate | Registered |
| Priya Shah  | HR Manager  | 22 Aug | Speaker  | Registered |
| Amit Jain   | Talent Lead | 23 Aug | Delegate | Registered |

This should make it very easy to identify HRs when their name is unclear.

---

# 8. New HR / Walk-In Addition

If a legitimate HR is not present in the existing database, the operator should have an option:

**ADD NEW HR**

Fields:

* Name
* Designation
* Company
* Email
* Mobile Number
* Address
* Role
* Attendance Date
* Invited By
* Remarks

Most fields should be optional because the registration desk should not unnecessarily block a legitimate HR.

However, at least enough information should be collected to identify the HR.

After saving:

**HR ADDED SUCCESSFULLY**

Then allow the operator to check them in.

---

# 9. Duplicate Check-In Protection

If an HR has already checked in, do not allow accidental duplicate entry.

Instead show:

**ALREADY CHECKED IN**

Display:

* HR name
* Company
* Check-in date
* Check-in time

Example:

"Ajay Sharma has already checked in at 10:42 AM."

---

# 10. Status Design

Use three primary states:

### GREEN — VERIFIED

The HR exists and can enter.

### YELLOW — POSSIBLE MATCH

The system found possible matches and the operator should verify the correct HR.

### RED/NEUTRAL — NO RECORD FOUND

No suitable record was found.

Do NOT make the interface aggressively say "Rejected" because the goal is to help the registration desk handle genuine HRs respectfully.

* Same name, different companies
* Same person attending both days
* Misspelled names
* Partial names
* Missing email
* Missing mobile
* Missing date
* Missing designation
* Missing company
* New walk-in HR
* Duplicate HR records
* Already checked-in HR
* Multiple HRs from same company
* Case-insensitive search
* Extra spaces in names
* Different name formats

Do not create a rigid system that blocks the operator unnecessarily.

* full_name
* company_name
* email
* mobile_number
